# 会議の開始通知と録音の自動停止

対象: Desktop（macOS アプリ）。録音の保存契約は [録音ストレージ](recording-storage.md)、音声の data flow は [Audio and Transcription Data Flow](../../architecture/audio-transcription-data-flow.md) を参照する。

自動停止は、停止漏れを許容して誤停止を避ける補助機能である。設定は既定オフとする。手動停止、致命的なキャプチャ障害時の停止、録音データの保存処理は自動停止と独立して動く。

## 検知

開始通知と自動停止は、同じ正規化済みプロセス遷移を使う。CoreAudio の入力中プロセス一覧の差分から、対応コンテキストの出現を開始通知に、消失を自動停止の候補にする。端末全体のマイク利用、起動アプリ、ウィンドウタイトルを合成する開始検知は使わない。

- 対象のコンテキストは Zoom、Teams、Slack、Discord、Webex、FaceTime と、ブラウザ固有の入力プロセスを識別できるブラウザ（Chrome、Edge、Brave、Arc、Firefox など）。ブラウザは helper process の bundle ID からブラウザ単位へ正規化し、タブ、URL、会議サービスは識別しない。
- Safari は汎用 WebKit helper しか観測できず所有アプリを安全に特定できないため、対象外とする。
- 開始通知が有効な待機中、または自動停止が有効な実録音中に、約1秒間隔で入力中プロセスを確認する。経過時間は wall clock の補正に影響されない単調時計で計測する。
- 初回スナップショットは状態の確立に使い、開始通知は出さない。録音中なら自動停止の監視対象にできる。
- 同じ周期で複数のコンテキストが出現した場合は、固定の優先順位で一件へ集約する。
- ブラウザの開始通知は会議ウィンドウを要求しないため、会議以外のマイク利用も通知候補になり得る。

## 自動停止の条件

- 成功した問い合わせで4秒間連続して消失した場合に終了遷移とする。
- 録音と対象コンテキストがともに30秒以上継続し、録音中に監視した全コンテキストが消失した場合だけ、正常停止・保存シーケンスを開始する。
- 先に録音した場合は、後から現れたコンテキストを追加する。会議中に録音を始めた場合は、録音開始後の最初の成功照会で実際に観測したコンテキストを引き継ぐ。録音開始前から消失猶予だけで保持している状態は引き継がない。
- ブラウザは、ブラウザ固有の入力プロセスと対応する会議ウィンドウを30秒間連続して同時に観測した場合だけ停止監視へ登録する。資格の確定前にどちらかが消えた場合や問い合わせが失敗した場合は計測をやり直す。登録後の終了判定はブラウザ単位で、同一ブラウザの会議タブと別のマイク利用タブは区別しない。
- 列挙・照会中に音声プロセスが消え、CoreAudio が `kAudioHardwareBadObjectError` を返した場合は、そのプロセスだけを消失として扱う。他のプロセスと会議の追跡状態は保持し、通常の4秒の消失猶予を適用する。
- 問い合わせの失敗では停止せず、最後に確定した状態を保持して連続消失の計測をやり直す。
- 自動停止の無効化、手動停止、録音終了で、自動停止の追跡状態をリセットする。
- 対面・オフラインの会議、未対応アプリ、CoreAudio に入力プロセスを公開しない環境では自動停止しない。
- 設定は専用の UserDefaults キーに保存する。旧キー `automaticallyStopRecordingWhenMicrophoneStops` は参照しない。

## 診断

CoreAudio のプロセス一覧と各プロセスの `IsRunningInput` / `IsRunningOutput` の取得・リスナー登録は、OSStatus とともに `AudioProcessActivity` カテゴリへ記録し、「0件」と問い合わせ失敗を区別する。Dahlia 自身を含む全プロセスを記録するが、音声内容、文字起こし本文、資格情報は記録しない。

## 未適合・未検証

- 2026-08-03 の Zoom ネイティブ版の実機検証では、`us.zoom.caphost` と `us.zoom.xos` は CoreAudio のプロセスとして現れたが、会議中も `IsRunningInput` / `IsRunningOutput` は `false` のままで、状態リスナーも発火しなかった。入力状態を公開しない環境では自動停止は動かず、すべての環境で動作する保証はない。
- ミュート、長い沈黙、退出後もアプリが起動したまま、会議後に別アプリや別タブが音声を再生する、といった場面ごとの誤停止と停止漏れは、サービス別に検証していない。

## 却下した案

- `AVAudioEngineConfigurationChange` による終了判定: Dahlia のマイクエンジンやデバイス構成の変化の通知であり、会議の退出を表さない。
- `kAudioDevicePropertyDeviceIsRunningSomewhere`: Dahlia 自身のマイクキャプチャにも反応するため、会議アプリの終了判定に使えない。
- システム音声の無音時間: 全員の沈黙、ミュート、資料の黙読と会議終了を区別できない。猶予を長くしても誤停止が残り、短くすると録音欠落の危険が高まる。
- アプリの起動・終了: 会議アプリやブラウザは退出後も起動し続ける。
- ウィンドウタイトルだけによる停止: ブラウザ、言語、UI 更新で変わり、権限や表示状態の影響を受け、ネイティブアプリでは退出後も残る場合がある。
