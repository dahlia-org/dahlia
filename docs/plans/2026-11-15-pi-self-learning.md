# デスクトップの Pi に自己学習（メモリー・スキル改善・定期実行）を足す計画

対象: Desktop（macOS アプリの内蔵チャット。Pi を子プロセスとして使う部分）。
状態: 第 3 版。[1 回目のレビュー](2026-11-15-pi-self-learning-review.md)と [2 回目のレビュー](2026-11-15-pi-self-learning-review-v2.md)を反映した。実装・自動検証済み。モデル品質30会話の実測、実モデルの費用計測、実アプリの手動操作確認は未実施。現在の契約は [自己学習 ADR](../adr/desktop/pi-self-learning.md) と [定期実行 ADR](../adr/desktop/scheduled-agent-scope.md) を参照。
作成日: 2026-11-15。

Nous Research の Hermes Agent が持つ自己学習の仕組みを、Dahlia の内蔵チャットへ移す計画である。

## 方針

**まず Hermes と同じものを作る。** Hermes には先に運用して得た知見が入っている、という前提に立つ。

1. プロンプト、ツールの契約、学習が動く条件、更新の時の保護は、Hermes の原文と挙動をそのまま移す。短く書き直したり、別の形に置き換えたりしてから評価しない。
2. Dahlia に組み込むための変更は行う。Swift と GRDB への保存、Pi との接続、アカウントの境界、録音の優先がこれに当たる。
3. Hermes と意味が変わる所は、[Hermes と違える所](#hermes-と違える所)に 1 か所にまとめる。Hermes の挙動、変える理由、代わりの保護を書く。
4. 広げる案（検索型の大きなメモリー、会議をきっかけにした実行など）は、同じものを使ってから、実際の会話・費用・失敗例を見て判断する。[後へ回すもの](#後へ回すもの)に置く。

比較元は `NousResearch/hermes-agent` の `fd8a6c41ace59b476193c61002ce6a86d667b18a`（MIT）で固定する。

## 結論

1. 足すものは 3 つ。**メモリー**、**会話後のふり返り（学習）**、**定期実行**。過去の会話の検索は既にある。
2. 定期実行は**アプリ側が持つ**。Pi 側には Hermes と同じ `cronjob` ツールだけを置く。
3. スキルの変更は、Hermes と同じ `skill_manage` に一本化する。対話からの直接のファイル書き込みはやめる。
   並行する編集を守るには、すべての変更が同じ順番待ちを通る必要があるためである。
4. Dahlia が足す土台は 1 つ。**実行の種別**（誰が始めた実行か、何をしてよい実行か）をアプリが保存する。
   Hermes はセッションごとにエージェントが分かれるので要らないが、Dahlia は 1 つのスレッドに複数の起点の実行が混ざる。

## Dahlia が足す土台: 実行の種別

**起点**。`chat_runs` に `origin` を足す。値は `user`（人が送った）、`thread`（ほかのスレッドが頼んだ）、`schedule`（定期実行）。
上限は `origin` で数える。`thread` と `schedule` を合わせてアカウントに 3 本まで。`user` は今までどおり数えず、待たない。
ふり返りは背景ジョブなので別に 1 本。無人の実行は合計で最大 4 本になる。

**Item の所属**。`chat_items` に `runID` を足す。通常の入力、途中の差し込み、ツールの結果、結果の通知による自動の再開も含めて、作る時に入れる。
これで、Item がどの起点の実行に属するかを、保存した内容だけから決められる。役割（user か assistant か）や文面からは推し量らない。ほかのスレッドからの依頼も Pi には user の役割で渡るためである。
更新より前の、`runID` のない Item は由来が分からないものとして扱う。

**許可**。`chat_runs` に `profile` を足す。値は `interactive` と `scheduled`。ふり返りは同じ考え方で `review` を持つ。
実行を積む時に決まり、その実行の間は変わらない。承認方式を `fullAccess` に変えても `profile` の上限は超えない。

| | `interactive` | `scheduled` | `review` |
| --- | --- | --- | --- |
| `bash` | 可 | 不可 | 不可 |
| `write` `edit` | 作業フォルダ | 不可 | 不可 |
| `read` `ls` | 可 | 可 | 不可 |
| Dahlia の会議ツール | 読み取りは承認なし、書き込みは承認方式による | 読み取りだけ | 不可 |
| 外部の MCP | 読み取りは承認なし、変更は承認方式による | 読み取りだけ。変更は聞かずに断る | 不可 |
| `memory` | 可 | 不可 | `add` は反映、`patch` と `remove` は承認待ち |
| `skills_list` `skill_view` | 可 | 可 | 可 |
| `skill_manage` | 可 | 不可 | 可（ふり返りの保護つき） |
| スレッドの操作、`cronjob` | 可 | 不可 | 不可 |

**守らせ方**。3 か所で同じ表を見る。
1. 起動: `--tools` と Seatbelt の設定を `profile` から作る。
   `review` だけは、ツールの定義を親と同じにして実行の時に断る（Hermes と同じ。プロンプトのキャッシュを生かすため）。その代わり、Seatbelt は何も書けない設定にする。
2. 使い回し: プロセスを使い回す条件に `profile` を足す。違えば、実行していない時に開き直す。
3. 実行の直前: 拡張は起動時に渡された `profile` で `tool_call` を止める。Swift の橋も、呼ばれるたびに実行の `profile` を確かめる。

**アカウントと録音**。動かすのは選択中のアカウントだけ。選択していないアカウントの予定とふり返り、録音中に来たものは「待ち」にして、戻った時・録音が終わった時に 1 回にまとめて動かす。

## 第 1 段階: メモリー

Hermes の契約をそのまま移す。変えるのは保存先だけである。

**表**。`agent_memories`。1 行が 1 件の覚え書き。
列は `id`（UUIDv7）、`accountID`、`target`（`user` か `memory`）、`content`、`createdBy`（`agent` か `user`）、`createdAt`、`updatedAt`。
Hermes はファイルに `§` で区切って入れる。Dahlia は行にする。同じアカウントで複数の実行が同時に書くので、書き込みを 1 つのサービスで順番に通すためである。
ツールから見える形（置き場ごとの件の並び、字数の上限、`old_text` で対象を決める）は Hermes と同じにする。
アカウント単位。バックアップと Server 同期の対象にしない。

**上限**。`user` 1,375 字、`memory` 2,200 字。超える書き込みは断り、今の全件を返す。自動では消さない。

**ツール**。`memory`。引数と説明文は Hermes の原文。

```json
{ "target": "user", "operations": [
  { "action": "add", "content": "..." },
  { "action": "patch", "old_text": "...", "content": "..." },
  { "action": "remove", "old_text": "..." }
] }
```

書き込みは橋を通して Swift の 1 つのサービスが行う。設定画面も同じサービスを使う。検査のパターンは Hermes のものを移す。

**注入**。プロセスの起動時に、両方の置き場の全件を、Hermes と同じ見出しと形で `--append-system-prompt` に足す。途中では差し替えない。
要約と画像解析には入れない。

**対話での手引き**。Hermes の原文をシステムプロンプトに足す。

**変更の記録と承認待ち**。表 `agent_learning_changes`。メモリーとスキルで共通に使う。
列は `id`、`accountID`、`kind`（`memory` か `skill`）、`target`、`before`、`after`、`status`、`source`（`interactive` か `review`）、`threadID`、`reviewID`、`createdAt`。
`status` は `applied`（反映した）、`pending`（承認待ち）、`discarded`（捨てた）、`reverted`（取り消した）。
Hermes の承認待ちの置き場と、スキルの変更の台帳を、この 1 つの表で受ける。

| 誰が | 操作 | 結果 |
| --- | --- | --- |
| 対話 | `add` `patch` `remove` | 反映して記録する |
| ふり返り | `add` | 反映して記録する |
| ふり返り | `patch` `remove` | 対象の行と今の内容を固定して `pending` にする。**誰が足した行でも同じ** |
| 利用者（設定画面） | 承認 | 固定した内容と今の内容が同じなら反映。違えば反映せず、両方を見せる |

承認待ちの保存に失敗した時は、その操作を断る。既にある行は残る。
設定画面で人が書いたか直した行は `createdBy = user` になる。これは表示に使うだけで、保護の強さは変えない（ふり返りの `patch` と `remove` は、どの行でも承認待ちになるため）。

**画面**。設定の「Dahlia AI」に「メモリー」のタブ。
置き場ごとの一覧と字数、追加、編集、削除、全削除。承認待ち（承認・捨てる）と最近の変更（取り消し）。見出しでの区切りは使わない。

**入・切**。

| 設定 | 切にすると |
| --- | --- |
| メモリー | 注入しない。`memory` を渡さない。ふり返りはスキル用の指示だけで動く。行は消さない |
| 会話の後に自動で学習する | ふり返りを予約しない。待っている予約を消す。動いているふり返りを止める。反映済みの変更と承認待ちは残る |

## 第 2 段階: スキルの管理とふり返り

### スキルのツール

`skills_list`、`skill_view`、`skill_manage` を拡張に足す。引数、説明文、上限（名前 64 字、説明 1,024 字、`SKILL.md` 100,000 字、補助ファイル 1 MiB）は Hermes の原文。

**すべての変更を 1 つのサービスに通す。** `skill_manage`、取り消し、設定画面からの操作は、橋を通して Swift の 1 つのサービスが行う。
このサービスは、1 つのスキルについて、次を 1 つの順番待ちの中で行う。保護の確かめ、今の内容の読み込み、変更、検証、変更の記録、置き換え。検証に失敗したら元に戻す。
ハッシュを確かめてから書くまでの間に、ほかの書き込みは入れない。

**対話からの直接の書き込みをやめる。** 今は対話の `write` `edit` `bash` が `pi/skills/` に書ける。これを読むだけにして、スキルの変更は `skill_manage` だけにする。
直接の書き込みを残すと、同じ順番待ちを通らないので、ふり返りが反映する直前に対話が書いた変更を消してしまう。
同梱の `skill-creator` は、`skill_manage` を使うように書き直す。2026-11-12 の決定（`pi/skills/` に書ける）を変えるので、ADR に書く。
利用者が外のエディタで直すことまでは止められない。サービスは書く直前に読み直すので、失われるのは、読み直しから置き換えまでのごく短い間の編集に限られる。

**スキルごとの状態**。表 `agent_skill_states`。列は `accountID`、`name`、`createdBy`（`agent` か `user`）、`locked`。
Hermes の `.usage.json` のうち、保護に要る 2 つだけを移す。設定の「スキル」タブに、ロックの入・切と、変更の一覧と取り消しを足す。

**ふり返りでの保護**。Hermes と同じにする。
- 書く前に、その回のうちに `skill_view` で対象を読んでいなければ断る。
- 削除は、`createdBy = agent` のスキルだけ。
- ロックしたスキルは、対話でもふり返りでも変えられない。

**同梱とパッケージのスキル**。読むだけで、変えられない（今の決まりのまま）。
Hermes の指示は「読み込んだスキルをまず直す」と言う。対象が同梱かパッケージのスキルだった時は、`skill_manage` が断り、「アカウントのスキルとして別の名前で作る」と返す。

### 動く条件

Hermes と同じ 2 つの数を、スレッドごとに数える。プロセスが閉じても消えないよう、`chat_threads` に 2 列足す。

| 数 | 増える時 | 0 に戻る時 | しきい値 |
| --- | --- | --- | --- |
| 利用者の発言の回数 | `origin = user` の実行で、利用者の発言が来た時 | `memory` を使った時、メモリーのふり返りが動いた時 | 10 |
| ツールを呼んだ反復の回数 | `origin = user` の実行で、エージェントがツールを呼んだ応答ごと | `skill_manage` を使った時、スキルのふり返りが動いた時 | 10 |

`origin = user` の実行が終わった時に、届いた数を見て指示を選ぶ。メモリーだけ届けばメモリー用、スキルだけならスキル用、両方なら両方用。
スキル用だけの時は `memory` を使わせない。
`origin` が `thread` と `schedule` の実行では、数えず、動かさない（Hermes が cron と子エージェントで動かさないのと同じ）。

ふり返りは `jobs_background` に置く。アプリを閉じても次の起動で動く。選択していないアカウントと録音中は待ちになる。
設定の例ではスキルのしきい値が 15 だが、コードの既定は 10 なので 10 にする。

### 動かし方

Hermes と同じく、**会話全体の写し**を渡す。前回のふり返りより後の分だけには絞らない。
絞ると、境界をまたいだ「失敗 → 直す → 成功」や、「さっきの方法で」という訂正の指す先が欠けるためである。

- 実行が終わった時、そのスレッドで何も動いていない間に、Pi のセッションの写しを取る。同時に、そこまでの `seq` を控える。
- ふり返りは、その写しを開く別のプロセスで動く。元のスレッドのプロセスは使わない。次の発言が来ても止めない。
- モデル、推論の強さ、システムプロンプト、ツールの定義は、元のスレッドと同じにする。使えるツールは実行の時に `memory`、`skills_list`、`skill_view`、`skill_manage` に絞る。
- 指示は、Hermes の原文に、Hermes と同じ後書き（使えるツール以外は断られる、という 1 文）を足して送る。
- 写しの中の、`origin` が `user` でない実行に属する Item と、由来が分からない Item には、機械からの入力だと分かる札を付ける。
- 終わったら写しを消す。

Pi で同じモデルの写しが使えない時（事前の確かめ 1）は、GRDB の `chat_items` から会話全体を組み立てて渡す。これは Hermes が別のモデルに要約を渡す道に当たる。

**上限**。反復は 16 回まで。入力の合計は、モデルの窓の 75%（最大 600,000 トークン。窓が分からなければ 120,000）。
届いたら、その場で終える。それまでに反映した変更は残る。数は既に 0 に戻っているので、やり直さない。次に数が届いた時に、また会話全体を見る。

**同じ変更を重ねない**。ふり返り 1 回に id を振り、変更の記録と通知に持たせる。背景ジョブがやり直しても、同じ id の変更と通知は 2 度作らない。

**知らせ方**。反映か承認待ちがあった時だけ、元のスレッドに通知の Item を 1 件足す。初めての時は、自動の学習が入であることと切り方を書く。

**初期値が入であること**。更新の時、数は 0 から始める。過去の会話をさかのぼって動かすことはしない。

### 質の確かめ

試験用の会話を用意する。実際の会話は使わず、作った会話にする。メモリーとスキルで期待が違うので、分けて見る。
Hermes は、メモリーには慎重さを、スキルには積極さを求めている。

| 組 | 元の決まり | 期待 |
| --- | --- | --- |
| メモリー: 利用者が続く好みを述べた（「今後は」「いつも」） | 根拠のある事実を保存 | `user` に 1 回だけ保存 |
| メモリー: ツールの結果で確かめた環境の事実 | 同上 | `memory` に保存 |
| メモリー: 話題や口ぶりから人柄を推し量れる | 推し量らない | 保存しない |
| メモリー: 1 回限りの頼み | 続く好みにしない | 保存しない |
| メモリー: 外から来た文章の中にだけ指示がある | 根拠は発言かツールの結果 | 指示としては保存しない |
| メモリー: 既にある行と食い違う | 無人では変えない | 承認待ちになり、行は変わらない |
| スキル: 読み込んだスキルの手順を利用者が直した | 読み込んだスキルをまず直す | そのスキルを `patch` |
| スキル: 失敗の後に、使い回せる手順を見つけた | 積極的に更新 | 既存に足すか、新しく作る |
| スキル: 環境のせいの失敗、道具への否定、一時的なエラー、1 回限りの作業、解決しなかった試行 | 残さない | 何も書かない |
| スキル: 同梱のスキルを直したくなる | Dahlia の決まり | アカウントのスキルとして作る |

各組 3 本、合わせて 30 本。外から来た文章の組と、承認待ちの組は、必ず満たす条件にする。ほかは、届かなかった数と外れた会話を記録に残す。

## 第 3 段階: 定期実行

### アプリ側が持つ理由

Hermes の予定表は、常駐するゲートウェイが 60 秒ごとに見る。Dahlia には常駐するものがなく、Pi にもない。
アカウント、認証、Seatbelt、MCP の許可、実行の枠は、アプリが持っている。時計もアプリが持つ。

### ツール

`cronjob`。操作は Hermes と同じ `create` `list` `update` `pause` `resume` `remove` `run`。
引数は、`schedule`、`prompt`、`name`、`skills` を移す。配信先やスクリプトなど、Dahlia にない引数は受けない。

予定の書き方は Hermes と同じにする。

| 書き方 | 意味 | 実装 |
| --- | --- | --- |
| `30m`、`every 2h` | 繰り返し | 分に直す。下限は 15 分 |
| `every monday 9am`、`weekdays at 9am` | 曜日と時刻 | Foundation の `Calendar.nextDate(after:matching:)` |
| 日時 | 1 回だけ | 時刻を持たない書き方は、Mac の今のタイムゾーンで読む |
| 5 項目の cron 式 | | 初めは受けず、理由を返す。Hermes も `croniter` がない時は同じように断る |

### 表

`chat_schedules`。列は `id`、`accountID`、`threadID`、`name`、`schedule`（書いたとおりの文字列）、`prompt`、`skills`、`revision`、`enabled`、`nextFireAt`、`createdAt`、`updatedAt`。

`chat_schedule_fires`。列は `scheduleID`、`fireKey`、`revision`、`runID`、`status`、`resultSeq`、`createdAt`。`(scheduleID, fireKey)` は 1 件だけ。
`status` は `queued`（待ち）、`running`、`delivered`（知らせた）、`silent`（静音）、`failed`、`interrupted`、`skipped`（古くなって捨てた）。

### 発火

時刻が来たら、1 つの transaction で次を行う。

1. `chat_schedule_fires` に `(scheduleID, fireKey)` を足す。既にあれば何もしない。
2. その予定の `queued` が既にあれば、新しく積まない（待ちは最大 1 件）。なければ、`origin = schedule`、`profile = scheduled` の実行を積む。
3. `nextFireAt` を次の時刻にする。

実行は、始める直前に、予定が入のままか、`revision` が同じか、アカウントが選択中かを確かめる。違えば始めずに `skipped` にする。
予定を止める・消す・変えると、`queued` は `skipped` にする。動いている実行は止めない。

**再起動の時**。今の復旧は `queued` も `interrupted` にする。`origin = schedule` の `queued` だけは別に扱う。
- まだ始まっていなかった分は、入・`revision`・アカウントを確かめ直して、予定ごとに最大 1 件を待ちに戻す。
- 始まっていた分は、今までどおり `interrupted` にして、やり直さない。
- 対話と、ほかのスレッドが頼んだ実行の復旧は変えない。

閉じていた間と眠っていた間の分は、次に動いた時に 1 回だけ実行する。

### 実行

Hermes と同じく、**発火のたびに新しいセッション**で動かす。前の実行の会話は引き継がない。

- 送る内容は、Hermes の cron の指示（原文）、前回の結果、予定の `prompt` の順。
- 前回の結果は、その予定の、静音でない最後の結果。8,000 字まで。Hermes の前置き（原文）を付ける。
- `skills` に挙げたスキルを読み込ませる。
- 終わったら、Pi の再開用のファイルは残さない。

### 結果の届け方

予定 1 つに、結果を並べるスレッドを 1 つ作る。これは見るための場所で、Pi の会話ではない。
このスレッドには送信できない。結果について話したい時は、新しいスレッドで `thread:<id>` を付けて頼む（既にある仕組み）。
こうすると、対話と定期実行が同じ Pi のプロセスを使うことがなく、外から来た文章が対話の文脈に勝手に入ることもない。

**静音と失敗**。判定は Hermes と同じにして、実行が終わる 1 か所（`endRun`）で行う。結果は `chat_schedule_fires.status` に保存する。
- 静音: 返事の全体、最初の行、最後の行のどれかが `[SILENT]`、`SILENT`、`NO_REPLY`、`NO REPLY`。文の途中にある時は静音にしない。
- 失敗: 最初の行がちょうど `[CRON_FAILURE]`。

**印と通知**。`chat_threads` に、利用者が最後に見た `seq` を足す。
印を出すのは、`status = delivered` で、`resultSeq` が最後に見た `seq` より大きい発火がある時。保存した状態から決まるので、読み込み直しても再起動しても同じになる。
静音の結果では、最後に見た `seq` を動かさない。その前にある普通の結果の印を消さないためである。
macOS の通知は、既にある会議の通知の仕組みに 1 種類足す。予定ごとに入・切できる。

### 確かめ

- 利用者が確かめる対象は、`prompt`・`schedule`・`skills`・使える接続先とツールの組。この組に `revision` を振る。
- `create`、`resume`、そして入のままの `update` は、承認方式が `fullAccess` でも必ず確認のカードを出す。
- 確かめた時に見えていた接続先とツールを控える。あとで増えたツールは使えない。
- `cronjob` は `interactive` の実行にだけ渡す。

### 画面

設定の「Dahlia AI」に「定期実行」のタブ。一覧、入・切、今すぐ実行、削除、結果を開く、待っている理由、最後の結果。

## Hermes と違える所

意味が変わる所の一覧。これ以外は Hermes と同じにする。

| 所 | Hermes | Dahlia | 理由 | 代わりの保護・確かめ方 |
| --- | --- | --- | --- | --- |
| メモリーの保存先 | ファイル 2 つ | GRDB の行 | 複数の実行が同時に書く。アカウントごとに分ける | ツールから見える形は同じ。上限と全部成功か全部失敗のテスト |
| スキルの変更の入口 | `skill_manage`。ファイルの道具でも書ける | `skill_manage` だけ | 並行する編集を守る（F2） | 反映の直前に別の編集を差し込む試験 |
| 同梱・パッケージのスキル | 読み込んだスキルを直す | 変えられない。別の名前で作る | 今の Dahlia の決まり | 試験用の会話 |
| ふり返りのプロセス | 同じプロセスの中の分身。次の発言で止まることがある | 写しを開く別のプロセス。止めない | Pi は 1 プロセス 1 会話 | 写しが取れるかの事前の確かめ |
| ふり返りで読めるファイル | 読むだけのファイル操作も可 | スキルのツールだけ | 作業フォルダや DB を無人で読ませない | `skill_view` で補助ファイルも読める |
| ふり返りの対象 | セッションごと。cron と子は別のエージェント | `origin = user` の実行だけ数える。ほかの Item には札 | 1 つのスレッドに起点が混ざる（F3） | 3 種類の起点を混ぜた試験 |
| 時計 | 常駐のゲートウェイが 60 秒ごと | アプリの背景ジョブ。閉じている間は動かない | 常駐するものがない。利用者の決定 | 閉じていた分は 1 回 |
| 予定の実行で使える道具 | cron と配信の道具以外は使える | 読み取りだけ。`bash`、書き込み、`memory` は不可 | 外の文章を読む実行が、会議の DB を読めて、通信もできる | `profile` の 3 か所の確かめ |
| 予定を作る時 | 承認なし | 必ず確認のカード | 無人の実行を先まで許す操作 | 変えた時の再確認の試験 |
| 結果の届け先 | 作った会話や、ほかの配信先 | 予定ごとのスレッド | 配信の仕組みがない | 印と通知 |
| 動かすアカウント | 1 つの利用者 | 選択中のアカウントだけ | 今の Dahlia の決まり | アカウントを切り替える試験 |
| 録音中 | 関係なし | 見送る | 録音を最優先（T3） | 録音が終わると 1 回動く |

## 残る危険

1. **`readOnlyHint` は、ツールを出す側の申告である。** 「読み取りだけ」は情報を外へ出させない保証ではない。だから、予定ごとに確かめた接続先とツールを控える。
2. **外から来た文章からの学習は、指示の文面で抑えている。** Hermes と同じ強さである。ツールの結果で確かめた事実は学ぶが、その中の命令には従わない、という区別はモデルの判断に頼る。試験用の会話と、取り消しで支える。
3. **対話の `bash` が通信できること**は、この計画の外である。ADR で別の課題として挙げる。
4. **Hermes の知られた問題は、題名しか確かめていない。** 機械が作ったターンから学ぶ（#150577）は `origin` で、`[SILENT]` が「異常なし」の報告まで消す（#53230）は予定の `prompt` の書き方で、それぞれ抑える見込みだが、本文は読んでいない。

## 後へ回すもの

同じものを使ってから、実際の会話・費用・失敗例を見て判断する。

- **検索型の大きなメモリー、5 つの型への分類。** 第 2 版の案。「顧客が多いとすぐ埋まる」は測っていない。上限に当たった回数と、消された行を見てから決める。
- **会議をきっかけにした実行**（始まる前、終わった後）。第 2 版の案。予定の表はそのための形にしない。
- **スキルの整理**（使われないスキルをしまう。Hermes の Curator）。スキルが増えてから。使った回数の記録もその時に足す。
- **書き込みの承認制**（Hermes の `write_approval`。既定は切）。
- **予定ごとの変更操作**（返信の下書きなど）。
- **5 項目の cron 式。**
- **取り消した割合を画面に出す。**
