# Dahlia Bot（AI 秘書）

対象: macOS の内蔵 Pi。Local Account / Server Account 共通。Private Web / Electron は内蔵 Pi がないため対象外。
状態: 3A-0、3A-2、3A-5 を実装・自動検証済み（2026-11-23）。3A-1、3A-3、3A-4、3B 以降は未着手。実モデル（isaac の Claude Opus 5.5）では、本物の Pi と Dahlia の拡張機能で Router と Worker を動かして確かめた（2026-11-23）。Router は3回とも、依頼と顧客の質問をそれぞれ案件にし、指示を埋め込んだニュースレターを閉じた。Worker は、許された Gmail だけを読み取り専用で検索して報告した。実アプリでの画面の確認が残る。
前提: [Always-on エージェント](2026-11-19-always-on-agent.md)の段階0〜2（取り込みまで）が土台になる。この計画は、その段階3以降を置き換える。
アプリ起動中だけ動く。常駐 daemon とクラウド実行は作らない。

## コンセプト

Dahlia Bot は、1人のユーザーに仕える AI 秘書である。仕事もこなすが、中心は本人の時間と約束を守ることに置く。

| | AI Coworker（Genie One など） | Dahlia Bot（AI 秘書） |
| --- | --- | --- |
| 仕える相手 | 組織の業務。頼まれた仕事をこなす同僚 | 1人のユーザー |
| 動く場所 | クラウド。PC を閉じても動く | 本人の Mac。本人のサインインで、アプリが開いている間だけ |
| 強み | 統制されたデータの分析、成果物の作成、業務アプリの操作 | 会議で実際に話された内容。誰が何を約束したか |
| 仕事の単位 | タスクと成果物 | 用件、約束、作業 |
| 既定のふるまい | 頼まれたら実行する | 黙って見ていて、判断が要るときだけ声をかける |

統制されたデータの分析と、クラウドでの常時実行は作らない。資料作成や調査のような作業は、本人の用件と会議に結び付いたものを引き受ける。Dahlia にしかない材料は会議記録なので、会議を起点にする。

## 用語

[Always-on エージェントの用語](2026-11-19-always-on-agent.md#用語)に、次を足す。

| 名前 | 役割 | テーブル |
| --- | --- | --- |
| Item（用件） | ユーザーに見せる1件。質問、承認待ち、報告、提案のどれか。インボックスの1行 | `agent_user_inbox` |
| 約束 | 会議で誰かが引き受けたこと（誰が・何を・いつまでに）。Task の一種として持つ | `agent_tasks` |
| 作業 | 調査や資料作成など、成果物を伴う仕事。Task の一種として持つ | `agent_tasks` |
| 成果物 | 作業の結果。Dahlia の中に下書きとして置き、報告の Item に付ける | 未定（[未解決事項](#未解決事項)） |
| 待ち | 「来たら教えて」「期限までに来なければ知らせて」。条件と期限を持つ Timer | `agent_timers` |
| 見回り | 読み取り専用の定期実行。気づいたことを提案の Item にする | — |
| 手引き | 秘書への常設の指示（Orca の `SOUL.md` に当たる）。ユーザーだけが書く | アカウント別の設定 |

インボックスは、これまで「テーブルを持たない表示」としていたが、`agent_user_inbox` の表示に改める。

## 決まり

### Item

- 種類は、質問・承認待ち・報告・提案の4つ。状態は、未対応・済み・却下。「あとで」（通知を延ばす）は 4 の1日のリズムと一緒に入れる。
- 質問は1件に1つの判断だけを尋ねる。選択肢と、おすすめを付けられる。
- 承認待ちの Item は Action を1つ指す。Action が済むと Item も済みになる。
- Item を作れるのは Router と見回りだけ。Worker は結果イベントで返し、Item にするかは Router が決める。
- 承認待ちの Action と「結果不明」は、Router の判断にかかわらず Item にする。
- 「放置されている」は状態として持たず、最後の動きからの日数で導く。
- 却下した提案は、同じものを30日は出さない。放置された提案は3日で消す。
- ユーザーの操作（回答、承認、却下、あとで）は、操作イベントとして inbox に追加する。

### Item への回答の届け方

承認待ち以外の Item（質問、提案）への回答は、Action を通らない。次の経路で届ける。

- Item は、回答の届け先の Task と、内容の版を持つ。Task を持たない Item（見回りの提案など）の届け先は Router とする。
- 回答の操作イベントは、Item の ID、版、選んだ選択肢か自由文を持つ。
- コードが1つの transaction で、版が今の Item と一致し、Item が未対応であることを確かめ、回答を Item に保存して済みにする。一致しなければ何も変えない。
- 回答のイベントは、届け先の Task が進行中ならその Worker に、終わっていれば Router に届ける。配送済みと処理済みの区別、再起動後の再配送は、ほかのイベントと同じにする。
- Worker は回答を受け取って再開する。同じ Item への2回目の回答は届かない。
- 約束の提案を認める操作も同じ経路を通る。認めた時点で、その約束の Task を進行中にする。

### 会議を起点にする Source

MCP を使わず、Dahlia のデータだけを読む。外部には何も書かない。

- **カレンダーの予定**: 開始前に、同じ予定と Project の前回の要約、双方の未完の約束、参加者との最近の用件をまとめた報告を作る。
- **要約の保存**: 保存された要約から「誰が・何を・いつまでに」を拾い、約束として記録する。相手の約束には待ちを置く。自分の約束は、期限が近づいたら下書きを用意する。
  - 契機は会議の終了ではなく、要約の版の保存とする。要約は、録音の停止後に文字起こしと生成を経て保存され、あとから手動で生成や再生成もされる。
  - イベントの外部 ID は、会議の ID と要約の版の組とする。同じ版は1回しか処理しない。
  - アプリの起動時と毎分の確認で、まだイベントになっていない現在の版を拾う。アプリを閉じていた間に保存された要約も、これで回収する。
  - 再生成された要約は、新しい版として処理する。前の版から拾った約束と同じものは、提案し直さない。
  - ユーザーが認めた約束と却下した約束は、再生成で黙って書き換えない。内容が変わったと見えるときは、変更の提案として出す。
- 人物の台帳は作らない。約束は会議と用件ごとの記録に留め、同じメールアドレスを1人にまとめない（PRODUCT.md の T2）。
- 拾った約束は提案の Item として見せ、ユーザーが認めたものだけを追跡する。

### Router と案件の進め方

既存の Router（全体を見る振り分け）と、Orca bot の「会話ごとに続くスレッド」を組み合わせる。
正確さと全自動化を、LLM の呼び出し回数より優先する（2026-11-23 ユーザー指示）。

- **振り分け**: 担当の決まった会話の続報は、その案件に直接届ける。それ以外は、tool だけを持つ Router がまとめて判断する。コードで先に振り分ける決まりは作らない。
- **案件の始め方**: Router は、ユーザーが望むと分かる用件は、頼まれていなくても自分で案件にする。望むかどうか判断がつかないものだけ、提案（`task_suggest`）にする。提案した案件のイベントは保留になり、ユーザーが認めると案件が始まり、却下すると処理済みになる。もっと確認させたいときは、手引きに書く。
- **案件のスレッド**: 案件ごとに、秘書のスレッドの子として、読み取り専用のスレッドを1本持つ。Worker はそのスレッドの run として動き、会話をスレッドに残して続ける。チャットの待ち行列で、無人の run と合わせて3本まで並行する。ユーザーはスレッドを開いて経過を読める。案件への追加の指示は、秘書のスレッドかインボックスから送る。
- **秘書のスレッド（Home）**: ユーザーと秘書の通常のチャット。各ターンの頭に、進行中の案件とインボックスの未対応の Item を、前回から変わったときだけ入れる（Pi にだけ渡し、履歴には残さない）。`secretary_request` で依頼を出し、案件の ID を付ければその案件への追加の指示になる。

### 作業

会議のための資料作成や、顧客からの質問に答えるための調査などを引き受ける。

- **入口**: ユーザーがチャットかインボックスから頼むと、依頼のイベントとして inbox に入る。Router が Task にする。会議前の準備や顧客の質問から、Router が作業を提案の Item として出すこともできる。
- **調べてよい範囲**: Task ごとに、Worker が読める読み取り専用の MCP サーバーを Router が決める。選べるのは、ユーザーが設定で許可したサーバーだけ。Dahlia の会議記録は常に読める。
- **Web 検索**: ユーザーが許可していれば、承認なしで使える（2026-11-23 ユーザー承認）。検索語は外部に送られるので、メールなどを読んだ Worker の検索語を通じて情報が外に出る経路になる。このリスクを受け入れたうえで、検索語に本文や個人を特定する内容をそのまま入れないよう Worker に指示する。
- **成果物**: Dahlia の中に下書きとして置き、報告の Item に付けて見せる。ユーザーが直せる。
- **外に出す操作**: Google Docs の作成や共有などは、ほかの書き込みと同じく Action として1回ずつ承認する。
- **上限**: Task ごとに時間とトークンの上限を持つ。超えたら途中経過を報告して止め、続けるかをユーザーに尋ねる。
- 作業の Worker も、bash、ファイルの書き込み、memory、skill 編集は使えない。

### 待ち

- Worker と Router が置く。何を待つか（Topic、送信者など）と期限を持つ。
- 置くときに、両方の結末で何をするかを書く。
- 終わり方は、成立・期限切れ・取消の3つで、どれか1つにしかならない。
  - 成立: 条件に合うイベントが来た。
  - 期限切れ: 期限までに来なかった。
  - 取消: 置いた Task が終わった、またはユーザーが取り消した。
- 終わり方の確定と、置いた Task への結果イベントの追加は、1つの transaction で行う。成立した待ちに期限切れは届かない。
- 期限の判定は、取り込みのあとに行う。待ちが見ている Source が、期限より後の時刻まで読み終えてから、期限切れにする。アプリを閉じていた間に返信が来ていた場合に、期限切れと誤らないためである。
- Source が無効か、読めない状態が続くときは、期限を過ぎた時点で「確認できなかった」と付けて期限切れにする。

### 見回り

- 読み取り専用で、決めた時刻に動く（既定は平日の日中に数回）。録音中は動かない。
- 使えるのは、読み取り専用の tool と、提案を出す tool だけ。tool の層で強制する。
- 1回に出せる提案は5件まで。既定の関心は「ユーザーを待っているもの」（返事待ち、期限の近い約束、答えていない質問）。
- 過去の提案（未対応、採用、却下）を渡し、同じ提案を繰り返させない。

### 手引き（SOUL.md 相当）

- アカウントごとに1つ。設定の Always-on タブでユーザーが書く。AI からは書き換えられない。
- 書く内容の例: 優先する相手、口調、やらないこと、通知してよい時間帯、朝のまとめの時刻。
- Router、Worker、見回りの指示に入れる。「常設の指示であり、ユーザーの今の依頼より下」と明記して渡す。
- 変えたら、次の実行から効く。再開する Worker には、変更後の全文を渡し直す。
- 初回は、項目の見出しだけを入れたひな形を出す。

### 好みの学習

- 学ぶ元は、ユーザーの承認・修正・却下と、手引きだけ。外部の本文からは学ばない。
- 学んだ好みには、元になった用件をコードが付ける。モデルの自己申告は使わない。
- 既存のメモリーの変更記録と Undo に載せる。

### チャットとのつながり

- 秘書のスレッド（Home）で話しかけたとき、進行中の用件と未対応の Item を、会話の頭に入れる。
- 入れるのは、前回から変わったときだけ。件数と文字数を絞り、untrusted data として包む。
- 裏で動く実行と会話相手が、1人の秘書に見えるようにする。

### 1日のリズム

- 朝のまとめと、終業時の振り返りを、報告の Item として出す。時刻は手引きに従う。
- 録音中と、手引きで指定した時間帯は通知しない。Item は溜めておき、あとで見せる。

### 自分で止まる

- 続けて10回失敗した Source と見回りは、自動で無効にし、報告の Item を出す。

書き込みの関所、自動化レベル、Router と Worker の権限は、[Always-on エージェントの決まり](2026-11-19-always-on-agent.md#決まり)のままとする。

## 品質の指標

- 修正なし承認率
- 拾うべき用件を見逃した割合
- 無関係な会話を同じ Task にまとめた割合
- 会議から拾った約束のうち、ユーザーが認めた割合
- 提案のうち、採用された割合と却下された割合
- 未承認の外部書き込みの件数（常に0）

到達目標（stretch）: ユーザーが触るのは1日5件以下、修正なし承認率95%以上。

## 見送った案

- Worker への worktree の委譲、複数の bot が同じ部屋で話す仕組み: コード作業と複数人向けで、秘書には要らない。
- 依頼者の名前を書き込みに付ける仕組み: 利用者が1人である。
- クラウド経由のプッシュ受信: アプリ起動中だけ動く前提で、取り込みで足りる。
- 人物の台帳、相手ごとの履歴の名寄せ: PRODUCT.md の T2 に反する。
- 外部の本文からの好みの学習: 第三者が書いた文面で、秘書のふるまいが変わる。
- 夜間の記憶の整理を別に作ること: 既存の Curator とふり返りがある。
- コードで先に振り分ける決まり（Orca の automation のトリガー）: LLM の呼び出しを減らす仕組みで、正確さと全自動化を優先する方針に合わない。
- Router を複数にすること: 関係するメールと Slack が別の Router に届くと、同じ用件で案件が2つできる。
- Worker を専用の Pi プロセスで動かすこと: 案件の経過が残らず、チャットの待ち行列・停止・再起動の扱いと二重になる。

## 未解決事項

- 手引きを既存の「チャットへの指示」と分けて持つ。保存先は同じアカウント別の設定とする案だが、長さの上限は決めていない。
- 成果物の置き場。既存の Document を使えるかを 3A-4 の前に確かめる。使えなければ専用の保存先を作る。
- 作業の時間とトークンの上限の既定値。
- 会議の要約から約束を拾う精度。3A-1 の評価で最初に測る。足りなければ、文字起こしも読む。
- 要約の版の識別。Local Account は `summary_versions` の版を使える。Server Account で同じ版が取れるかは未確認で、3A-3 の前に確かめる。
- 再生成の前後で「同じ約束」とみなす基準。
- 会議前の報告を出す時刻（開始の何分前か）と、会議が続くときのまとめ方。
- `agent_user_inbox` の保存期間。済みと却下をいつ消すか。
- Router、見回り、会議の Source の1回あたりのトークン量。3A の各段階で計測する。2026-11-23 の実測では、イベント3件の Router が入力約5,800（大半がキャッシュ）・出力約1,500、メールを6回読んで報告した Worker が入力約95,000（うちキャッシュ読み73,000）・出力約1,900だった。
- 残るリスク: 自由文を外部に送れる操作の自動化と、承認なしの Web 検索は、情報持ち出しの経路になる。LLM による定期実行はトークンを使い続ける。
