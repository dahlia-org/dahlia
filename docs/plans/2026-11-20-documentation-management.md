# ドキュメント管理方針の見直し

対象: リポジトリ全体の文書（`AGENTS.md`、`PRODUCT.md`、`ARCHITECTURE.md`、`docs/`）。
状態: 2026-11-20、ユーザーの「改修を進めて」を受けて試行と一括移行を実施した。ユーザーのレビュー待ち。
完了条件: ユーザーが変更をレビューし、下の「残る判断」に回答すること。完了したら、この計画は方針の要点を `docs/README.md` と `docs/spec/README.md` に残して削除する。

## 提案の要点

現行契約と経緯を同じ文書に混ぜない。HEAD の文書は「いま守る契約」を現在形で書き、経緯は git と PR に任せる。
混在を解いた文書は判断の記録ではなくなるので、ADR という形式はやめる。

先に同期の 1 テーマで混在の解消を試し、効果を測る。効果があれば残りを一括で書き直す。
効果が見えなければ一括の書き直しはせず、追記をやめる規則と CI 検査だけを入れ、文書は変更のついでに直す。

## 現状の問題

coding agent の邪魔になっているのは、コードと食い違う古い記述ではない。現行契約と経緯が同じファイルに混ざっていることである。

2026-11-20、commit `8617515e` で測った。

| 測ったもの | 結果 |
| --- | --- |
| 直近 90 日のコミット | 494 件中 251 件が `docs/` を、215 件（44%）が `docs/adr` を変更。`shared/sync.md` は 47 回 |
| ADR の中の経緯 | 44 ファイル 3,006 行のうち、249 行に「旧・廃止・置換」など、200 行に日付 |
| 正本から ADR へのリンク | `ARCHITECTURE.md` 28、`PRODUCT.md` 20、`apps/server/AGENTS.md` 11 |
| 廃止した用語 Vault | 15 以上の文書に残る（正当な用法かは未判別） |
| 文書中の識別子がコードに無い割合 | ADR は 34 個中 0。全体で 164 個中 8 |
| リンク切れ | 29 件。確認した先頭 15 件は `docs/plans` のレビュー 2 ファイルにある別 worktree の絶対パス |
| CI の文書検査 | なし |

ここから読み取れること:

- ADR は判断の記録ではなく、実質「生きた仕様書」である。更新が多く、正本がルーティング先にしているため、エージェントは読み飛ばせない。
- 混在は運用ルールが作っている。`docs/adr/README.md` は「本文を整合させ、以前の選択と変更理由を日付付きで記録する」と定めている。
- `shared/sync.md` の冒頭は「以下の旧仕様はこの範囲に限り履歴として残す」と書く。どの段落が有効かを、読むたびに判断する必要がある。
- 廃止済みの `desktop/customer-intelligence.md` と `desktop/codex-runtime.md` が、索引で現役の文書と並んでいる。
- 識別子の乖離はほぼ無い。直す対象は鮮度ではなく、どの記述が有効かの区別である。

識別子の照合と Vault の集計は機械的な粗い集計で、個別には読んでいない。
「混在が誤動作の原因」は文書の構造からの推定で、まだ実測していない。下の試行がその検証になる。

## 外部の根拠

一次情報を確認したもの:

- [Evaluating AGENTS.md（ETH Zürich）](https://www.sri.inf.ethz.ch/publications/gloaguen2026agentsmd): コンテキストファイルは成功率を上げず、推論コストを 20% 以上増やす。著者は最小限の要件だけを書くよう勧める。
- [When Instruction Files Go Stale](https://arxiv.org/abs/2611.09802): エージェントは、正しい情報が他にあっても古い指示に従う。失敗からは回復するが、指示ファイル自体は直さない。
- [Harness engineering（OpenAI）](https://openai.com/index/harness-engineering/): `AGENTS.md` は約 100 行の目次にし、`docs/` を正本にする。鮮度は linter と CI で検査し、定期エージェントが古い文書を直す PR を出す。

一次確認していないもの: `AGENTS.md` で実行時間が 28% 減ったという報告（[arXiv 2601.20404](https://arxiv.org/abs/2601.20404)）。成功率ではなく効率の測定で、上の結果とは測る対象が違う。

## 方針

### 文書が区別して持つ 3 つの状態

`ARCHITECTURE.md` は normative な target state と現在の実装を分けている。テーマ別の仕様書も同じ区別を保つ。

| 状態 | 内容 | 書く場所 |
| --- | --- | --- |
| 守る契約 | ユーザーが承認した、いま有効な契約。実装済みかどうかを問わない | 仕様書の本文 |
| 未適合・未実装 | 契約と実装が違う箇所、まだ実装していない契約 | 仕様書の「未適合・未検証」節。横断的なものは `ARCHITECTURE.md` の Conformance Status |
| 未検証 | 実装したが、実機や実データで確かめていない項目 | 同じ節 |

コードは契約の正本ではない。契約と実装が違うときは、文書を実装に合わせて書き換えず、未適合として残す。

### 置き場所と寿命

| 情報 | 置き場所 | 寿命 |
| --- | --- | --- |
| 機械で判定できる規則 | test、lint、CI | コードと同じ |
| 守る契約、未適合、未検証 | テーマ別の仕様書 | 変更時に本文を書き換える |
| 却下した案 | 仕様書末尾の短い節。再提案されそうなものだけ | 前提が変われば削除 |
| 経緯、変更理由 | コミットメッセージと PR 本文 | 永続。HEAD には置かない |
| 計画、レビュー記録 | PR とブランチ | マージ後、下の引き継ぎを確認して削除 |
| 調査 | 日付付きの文書 | 下の引き継ぎを確認して削除 |
| エージェントへの指示 | `AGENTS.md`。ルーティングと、破ると data loss になる不変条件だけ | 現状を維持 |

### 書き方の規則

- 仕様書に「追記」「以前は」「置き換える」を書かない。変わった部分は本文を書き換え、理由は PR に書く。
- 日付は、ユーザーの承認日と実測日には書く。例: tenet の例外を承認した日、ベンチマークを取った日。これらは経緯ではなく、いま有効な事実の一部である。
- 廃止した機能の文書は削除する。
- 同じ契約を 2 か所に書かない。他の文書からはリンクする。

### 削除前の引き継ぎ

計画、調査、ADR を削除または書き直す前に、次の 3 点が残る先を確認する。確認できないものは削除しない。

1. 未解決事項と未完了の検証: 仕様書の「未適合・未検証」節へ移す。
2. 結論の根拠と限界: 結論を仕様書へ移すとき、限界も一緒に移す。例: [検索ランキング調査](https://github.com/dahlia-org/dahlia/blob/8617515e0afdc5c264a77e97d490e020881b020f/docs/research/2026-08-25-meeting-search-ranking-benchmark.md) は、採用値に加えて評価の循環性という制約を持つ。
3. 原文への参照: 削除直前の commit を固定したリンクを仕様書に 1 本残す。`docs/plans/README.md` が旧計画で使っている方法と同じ。

## 鮮度を保つ仕組み

- CI の文書検査: リンク切れ、絶対パス、廃止した用語、「追記」「旧仕様」などの語、索引への未登録。
- 定期エージェント: 仕様書とコードの食い違いを探し、小さな修正 PR を出す。食い違いは未適合として報告し、文書を実装に合わせて書き換えない。

## 試行

目的は、現行契約と経緯の混在を解くことの効果を測ること。対象は `shared/sync.md` と `shared/sync-priority.md`。

### 課題と正解表

- ひっかけ問題 10 問: 答えが途中で変わった論点（送信の優先度、競合解決の範囲など）。
- 通常の課題 3 問: 同期の契約に違反する差分のレビュー 2 問と、小さな変更の方針を答える 1 問。
- 正解表は承認済みの契約から作る。2 本の文書を突き合わせて現行の契約を確定し、各項目をコードと照合する。
- 契約とコードが違う項目は、契約を正解とする。違いは未適合としてユーザーに報告し、どちらが正しいかを勝手に決めない。

### 比較する条件

| 条件 | 文書 |
| --- | --- |
| A | 現行の 2 本 |
| B | 2 本の混在を解いた仕様書 1 本 |

- B は内容を足さない。現行の契約を現在形に直し、経緯を除くだけにする。別のエージェントが、A の現行契約が B にすべてあり、B に新しい事実が無いことを確認する。これで、誤りの訂正による改善を混ぜない。
- 各条件を、この会話の文脈を持たない新規セッションで 3 回ずつ実行する。モデル、プロンプト、他の文書は同じにする。
- 記録するもの: 正答率、ツール呼び出し数、読んだ行数。

### 判定

- B の正答率が A より高い、または同等で手数が減る: 残りの ADR を同じ方法で一括して書き直す。
- 差が見えない: 一括の書き直しはしない。追記をやめる規則と CI 検査を入れ、文書はそのテーマを変更するときに直す。

13 問を 3 回ずつの規模なので、傾向を見るための測定である。統計的な検定はしない。
混在を解くと文書は短くなる。短縮の効果と混在解消の効果は分けて測らない。どちらも同じ書き直しの結果だからである。

### 結果（2026-11-20）

| 条件 | 正答（各13点満点） | 平均トークン | 平均ツール呼び出し | 平均所要時間 |
| --- | --- | --- | --- | --- |
| A（現行の 2 本） | 12.5 / 13 / 12.5（計38/39） | 11.8万 | 14.0 | 137秒 |
| B（混在を解いた 1 本） | 12.5 / 12.5 / 13（計38/39） | 9.2万 | 11.3 | 103秒 |

- 正答率は同じで、B はトークンが約22%、ツール呼び出しが約19%少なく、所要時間が約25%短い。判定基準により一括移行した。
- ひっかけ問題は A でもほぼ正答された。正答率の差は、この問題の難しさでは測れていない。効果は手数の削減として出た。
- 書き直しそのものに誤りが入る。B の初稿は、照合で誤り 2 件（置換済みの規則を残した、容量の数え方が自己矛盾）と規則の欠落 12 件が見つかった。一括移行でも、書き直しごとに別のエージェントが元の文書と照合した。
- 採点は、条件を伏せた別のエージェントが正解表に従って行った。正解表を作ったエージェントは B を見ていない。

## 一括移行で行った作業

1. `docs/adr/` を `docs/spec/` に改名し、全ファイルを現在形の仕様へ書き直した。4 グループに分けて書き直し、グループごとに別のエージェントが元の文書と照合した。
2. 廃止した機能の仕様（Codex runtime、顧客インテリジェンス）と、統合した `organization-vaults.md` は、残る制約を移してから削除した。
3. 調査 4 本と、完了した計画 1 本・計画のレビュー記録 2 本は、結論・限界・未解決事項を仕様へ移してから削除した。録音自動停止の現在の契約は調査文書にしかなかったため、`docs/spec/desktop/recording-auto-stop.md` を新設した。
4. `AGENTS.md`、`PRODUCT.md`、`ARCHITECTURE.md`、`docs/README.md`、各 scoped `AGENTS.md` の ADR への言及と、tenet 変更規則（ユーザーの明示的な承認と承認日の記録）を書き換えた。
5. CI の文書検査（`scripts/check-docs.mjs`、`.github/workflows/docs-ci.yml`）を入れた。リンク切れ、見出しリンク切れ、端末固有の絶対パス、索引への未登録、`docs/spec/` 内の改訂履歴の語を検査する。
6. `PRODUCT.md` に、GA は Swift 製の macOS アプリだけで、ほかはアルファ版であることを書いた。

## リスク

- 却下理由が消えると、エージェントが却下済みの設計を再提案する。仕様書の「却下した案」の節で防ぐ。
- ユーザーの承認の記録が消える。承認日を本文に残す規則で防ぐ。
- 文書を再編しても成功率は変わらない可能性がある（ETH の結果）。だから先に測る。

## 採らなかった案

- ADR に status や superseded のメタデータを足す: Dahlia の ADR は番号なしでテーマ別に統合済みで、ファイル単位の状態では段落単位の混在を解けない。
- 試行で「ADR のまま混在を解く」条件を別に設ける: 1 テーマの試行では、新構成との違いが置き場所の名前だけになる。置き場所は試行の後に決められる。
- 完了した計画を HEAD に残す: 引き継ぎを確認して削除し、固定 commit へのリンクを残す。未解決事項は仕様書に残るので、通常の探索経路から消えない。
- ベクトル検索や文書用 MCP を入れる: 6,490 行なら grep と索引で足りる。
- `AGENTS.md` を短くする: ルートは 127 行で、すでに目次型である。

## 残る判断

- 各仕様の「未適合・未検証」に「未確定」として残した項目。元の文書からは現在の契約を決められなかったもので、ユーザーかその領域の担当者の判断が必要。
- 照合で見つかった、文書とコードの食い違いの疑い。文書をコードに合わせず、未適合として残している。
