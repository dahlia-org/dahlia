# チャットのスレッド管理と画面に依存しない実行

対象: macOS の内蔵 Pi チャット。Local Account / Server Account 共通。
判断: 2026-11-15 の計画で、Workspace 切替時の継続、結果通知による親の自動開始、ユーザー作成スレッドへの送信、
Local MCP への非公開をユーザー承認済み。rebase 後のアカウント単位への操作境界変更も同日承認済み。
状態: 採択・ローカル実装・自動検証済み。実アプリの手動操作確認は未実施。

## 理由と決定

1つの会話から別の会話に仕事を依頼し、結果を受け取れるようにする。画面の寿命が実行の寿命を決める構成では、
非表示の会話への依頼、結果通知、別画面からの途中参加を安全に扱えない。

PiChatService が run と承認を所有し、画面は再接続できる projection とする。購読者のない run も履歴へ保存する。
購読イベントは有界とし、遅い購読者を切断しても実行を中断しない。切断後は実行中の snapshot、または完了済みの保存履歴へ再同期する。途中参加は保存済み履歴・未確定本文・tool・承認と、
その後のイベントを一つの所有境界で取得する。
画面は自分のスレッドの状態だけに従う。service はスレッドごとに実行中・待機中・最後に確定した run を配信し、画面は
自分が最後まで表示した run と異なる run が確定したときだけ保存履歴を読み直す。他スレッドの活動では読み直さず、
読み直しはモデルと推論強度の選択を変えない。履歴一覧は新しいスレッドが現れたときだけ先頭から読み直す。アカウント切替はそのアカウント以外の実行と待機入力を停止する。

run の入力待機・依頼元・状態・重複排除・通知の配達は `chat_runs` に保存する。
run の終了（完了、失敗、停止、process の消失、開始の失敗）は service の1つの出口を通り、状態の保存、確定した run の配信、
待機中の run の開始、依頼元への配達を必ず行う。ユーザーによる停止は run の状態とは別に保存し、その run が始めた仕事の結果で
スレッドを自動再開しない。アカウントを切り替えた後に終了した run の結果は、戻ってきても自動配達しない。起動時に queued / running /
waitingForUser は interrupted とし、自動再実行しない。run とチャット履歴はバックアップ・Server 同期に含めない。

Pi extension の list / search / read / start / send / wait / interrupt / update は process に結び付いた bridge を通す。
caller の自己申告 ID で認可しない。新しい子は1段だけとする。子スレッドと、他スレッドから依頼された run は、スレッド操作を読み取りに限る（既存スレッドへ送った依頼からさらに子を作れない）。削除・承認応答は
エージェント用ツールにしない。子の承認方式は親より緩くせず、既存スレッドへの依頼でもその実行の承認方式を緩めない。

エージェントが開始する run はアカウント当たり3本とし、超過分は永続待機列へ入れる。ユーザー入力はその列を待たない。
ユーザーの1回の送信を起点とする run は、起点と通知による自動開始を含め合計12回までとする。

結果は状態と run ごとに確定・保存した応答の抜粋だけを通知する。親が wait 中なら戻り値へ渡し、実行中なら idle になるまで保留する。
通知による開始と配達の記録は同じ transaction で確定し、再起動後に同じ通知を再送しない。通知は別種の Item として
保存・カード表示し、通常の本文検索には入れない。他スレッドと通知を untrusted data とし、Auto review にも
ユーザーの許可として渡さない。queue / steer の依頼文は由来を持つ JSON envelope として送り、Auto review ではユーザー本文から分離する。

スレッド間の送受信は T3 Code の send / read / wait / interrupt を参考にし、次の点を変えて採用する。

- send の既定は auto とし、呼び出し元が依頼した実行中の run には steer、それ以外は queue とする。T3 Code の auto は実行中の
  turn へ無条件に割り込むが、Dahlia ではユーザーや別スレッドが開始した run へ割り込ませない。明示した steer も同じ条件で拒否する。
  応答の `delivery` で steered / queued を返す。
- 依頼元が依頼先の本文を末尾まで読んだ時点で、その確定済み run の結果を配達済みとする。T3 Code は読み取りで配達済みとするが、
  途中までのページや承認待ちの run は配達済みにしない。同じ結果による自動開始と run 予算の消費を避ける。
- wait は時間切れで終了を促す `next` を返す。結果は idle 時に自動で届くため、待機の繰り返しを主経路にしない。
  受け取り済みの結果では戻らず、新しい結果が届くか、待つ対象がなくなるか、ユーザーが停止したときに戻る。
- `client_request_id` はユーザーの1回の送信の中だけで有効な再送キーとする。同じキーを別のスレッド宛てに使うと拒否する。
  queue と steer のどちらで届けた場合も1回の配達として扱い、再送は `delivery: duplicate` を返して入力を届け直さない。
- 依頼された run の承認方式は依頼元のものを上限とし、依頼先のスレッドで選択済みの方式があればより厳しい方を使う。
  この上限は run の開始時だけでなく tool 呼び出しの承認判定のたびに、依頼元と親の現在の選択で計算し直す。
  依頼元や親を実行中に厳しくすると、実行中・待機中の依頼先にも次の tool 呼び出しから効く。
  依頼先で未選択の場合、依頼元の子は依頼元の方式を引き継ぎ、それ以外のスレッドは Auto review を上限とする。
  ユーザーがスレッドで選んだ方式は、そのスレッドの process が閉じてもアプリの起動中は service が保持する。結果通知による
  親の再開や、process のないスレッドへの依頼は、推測せずその方式を使う。アプリの再起動後は全スレッドが Auto review に戻る。
- interrupt は `run_id` で1件の run だけを取り消せる。省略時は依頼先の実行中の run と待機中の run をすべて止める。
- 結果通知の抜粋が上限に達した場合は `truncated` を返し、全文は read で読む。read は1件の本文が上限を超えると
  `item_cursor` と `text_offset` で続きを読める。切り詰めた本文がある間は配達済みにしない。
ユーザーの明示停止とアカウント切替では、該当 run の自動通知抑止を保存し、親の自動再開を起こさない。

承認待ちの要求は親・子の画面で同じ要求 ID を表示し、どちらも同じ service の decideApproval を通す。
先に応答した画面だけが確定できる。エージェントには状態と tool 名を返し、承認の判断や実行はさせない。

履歴とサイドバーは親子関係と実行状態を表示する。親の会話では依頼先の状態・開く・停止と承認操作を提供し、
入力欄の追加メニューから他スレッドを参照チップとして追加・削除できる。

## 実行の由来と定期実行

`chat_runs.origin` は user / thread / schedule、`profile` は interactive / scheduled を保存する。
`chat_items.runID` が所属を示し、旧 Item は由来不明とする。人の role や文面から由来を推定しない。
無人の3本の枠には thread と schedule を含め、対話は数えない。ふり返りは別に1本とする。
定期実行の結果 Thread は閲覧専用。発火は毎回新規 Pi session とし、再起動時は未着手の schedule だけ待ちに残す。
詳細は [定期実行](scheduled-agent-scope.md) と [自己学習](pi-self-learning.md) に従う。

## 操作境界

呼び出し元と同じ実行アカウント内の Thread を対象とし、Workspace をまたぐ一覧・参照・実行を許可する。
アカウント境界を超える操作は許可しない。同じアカウント内の Workspace 切替では実行を継続する。
元の計画の Workspace 境界は、rebase で取り込んだ #802 のアカウント単位チャットに合わせて廃止する。

Private Web / Electron の Server AI、Local MCP、Server MCP は対象外とする。

## 検証の境界

GRDB の使い捨て DB と fake Pi transport で保存・境界・購読・承認・待機列・配達を検証した。
実 Pi と隔離した loopback gateway で8ツールと画面なしの steer を確認し、既存 extension の回帰テストも通過した。
NSHostingView の追加メニュー操作テストは通常・小さいウィンドウを対象とする。署名済みアプリの手動操作は未確認。
