# Desktop Pi のメモリーと自己学習

採択: 2026-11-15。第3版プランに対する利用者の実装指示に基づく。
対象は macOS の内蔵 Pi チャット。Local Account / Server Account とも Mac 内のアカウント別に保存する。
Private Web、Electron、Local MCP、Server MCP、要約と画像解析には追加しない。

Hermes Agent の固定コミット、英文プロンプト、ツールスキーマ、検査パターンと差分は
[UPSTREAM.md](../../../apps/macos/Sources/Dahlia/PiExtension/hermes/UPSTREAM.md) を正本とする。
メモリーは user 1375字、memory 2200字（区切りを含む Unicode scalar 数）。一括操作は全部成功か全部失敗とし、成功時は本文を再提示しない。
設定の追加・編集画面は対象の種類と入力例を示す。長文は入力欄内でスクロールでき、保存・キャンセルの操作を同じ画面内に保つ。
無人の patch/remove は作者にかかわらず行と内容を固定した承認待ちにし、現在値が一致する場合だけ承認・取り消しを反映する。
メモリーと学習の初期値は入。無効化しても記録・承認待ち・反映済みの変更を消さない。
会話からのスキル更新・スキルの自動整理（Curator）・スキルの最適化は、設定のスキル → 自動最適化に、この順でそれぞれの実行履歴と並べる。
メモリーとそのふり返りは設定のメモリー（独立したページ）で、別々に切り替える。
メモリーとスキルのふり返り履歴は、それぞれの設定ページで種類を絞ってからページ分割する。種類を保存していない過去の履歴は、両ページの「以前の共通履歴」に残す。

スキル一覧はマイスキルと読み取り専用の同梱・パッケージを分け、変更履歴はスキル単位で折りたたんで表示する。
分ける前の1つの切り替えは、両方の初期値として引き継ぐ。
バックアップと Server 同期の対象外とし、Server の Dahlia Memory とは共有しない。

2026-11-12 の account skills への直接書き込み許可を置き換える。
スキルの変更・取り消しは同じ AgentSkillService を通し、検証・直前の読み直し・変更記録・置換を直列化する。
ファイル道具と bash には skills を読み取り専用で渡す。同梱・パッケージのスキルは別名コピーが必要。
編集と取り消しでは、画像などのバイナリを含め、変更しないファイルの内容と実行権限を保持する。設定でロックしたスキルは変更不可。ふり返りではその回で読んだ対象だけを書き、削除はエージェントが作ったものに限る。

利用者の発言とツールを呼んだ応答を別に数え、それぞれ設定の回数（上流の `memory.nudge_interval` と `skills.creation_nudge_interval`、初期値10）でメモリー／スキル／両方のふり返りを予約する。時刻では動かない。
ふり返りのモデルと推論の強さは、メモリーとスキルそれぞれにアカウント別の専用設定を持ち、会話の選択から独立させる。
初回はアカウントで利用可能なモデル（Haiku、Luna、その他の順で自分の provider を優先）を選んで保存し、推論の強さは medium。以後は明示的に変更するまで保持する。
以前の共通設定で明示したモデル・強さは両方の初期値に引き継ぐ。同時に条件を満たしたときも別々の背景ジョブとして直列実行する。
旧版の未着手の combined ジョブは、snapshot を保ったまま2種類へ分ける。
origin=user だけを数え、更新前の Item や機械の入力を人の発言として推定しない。
別の Pi プロセスに、全会話の GRDB snapshot と親のプロンプト・ツール定義を渡す。
Pi RPC には由来を付け直して複製する API がないため、計画にある GRDB fallback を採用する。
使える道具は memory とスキル道具だけ。16応答または累積入力が context window の75%（最大600000、不明120000）で止める。
レビューは既存の背景処理と別の1本。選択中アカウント・録音していない間だけ開始し、切替・無効化で止める。
再起動時、未着手は保持し、着手済みは再実行しない。完了後は snapshot を消し、変更があれば元のスレッドに一度だけ知らせる。

2026-11-18 追記: Hermes Curator を同じ固定コミットから移植する（利用者の指示により、上流をできるだけそのまま再現する）。
アプリの `Housekeeping` が1分刻みで動き、60回に1回、選択中アカウントについて判定する。
条件は `interval_hours`（初期値7日）の経過と、`min_idle_hours`（2時間、固定）の会話の無操作と起動からの経過。
初回は記録だけを残し、1回分の間隔を待つ。録音中・会話の実行中・ふり返り中は始めない。
1回の整理は、LLM を使わない遷移と、任意の統合パスからなる。遷移では、使われない期間で `active → stale → archived` と移す。
stale は14日（固定）、アーカイブまでは `archive_after_days`（初期値30日）。一度も使われていないスキルは、stale の期間より若い間はアーカイブしない。
アーカイブは `skills/.archive/` への移動とし、削除はしない。設定から戻せる。
統合（`consolidate`、初期値は切）では、上流の英文プロンプトと候補一覧を、スキル道具だけを持つ別の Pi process に渡す。
上限は100応答・30分とする。モデルと推論の強さは上流の `auxiliary.curator` に当たる設定で選べ、既定は Pi の既定モデルと未指定の強さ。
対象は、アカウントのスキル（`account`、上流の `agent`）のうち、ふり返りや統合パスが作ったもの（`createdBy='agent'`）だけ。
会話の中で作ったもの（`learn`）・手で作ったもの（`user`）・Dahlia 同梱（`bundled`）・Pi パッケージ（`package`、上流の `hub`）は対象外。
この更新より前からあるスキルは `user` とし、整理しない。マイスキルから上流の `adopt` と同じく対象に加え（`agent`）、外す（`user`、固定も外す）ことができる。固定・ロック・予定で使うスキルも触れない。
背景の処理による削除は、`absorbed_into` で統合先を示した場合だけ受け付け、アーカイブとして扱う。固定したスキルは、対話の操作でも削除できない。
使用の記録は、`skill_view`、SKILL.md の `read`、`/skill:` の入力、変更の回数と時刻。ただし統合パス自身の閲覧は数えない
（上流では、閲覧したスキルの時計が毎回戻ってしまうため）。上流の `prune_builtins`・全体の snapshot と rollback は持たない。
変更はスキルの変更記録から1件ずつ取り消す。予定のスキル参照も書き換えない（承認済みの予定を無人で変えないため）。
Curator とふり返りの実行は `agent_system_runs` に残す。チャット一覧と分けて30日で消すが、各種類の最新の1件は間隔の起点として残す。

未解決の危険: 外部の文章の命令と事実の区別は Hermes の指示とモデルの判断に依存する。
対話の bash の通信許可はこの変更では見直さない。外部エディタの直前検査後から置換までの競合は防ぎ切れない。

2026-11-19 追記: hermes-agent-self-evolution の Phase 1（SKILL.md を DSPy + GEPA で進化させる）を移植する。
上流の固定コミット、プロンプトと差分は UPSTREAM.md を正本とする。最適化のループは Pi 拡張（`skill-evolution.ts`）のチャットの道具 `skill_optimize` に置き、
アプリはスキルと会話を渡し、結果を承認待ちにするだけにする。DSPy と GEPA の Python は動かさない。
上流は CLI で手で動かすので、Dahlia でも利用者の会話の中でだけ動かす。設定のスキル → 自動最適化から始めると、新しいチャットで依頼を送る。
チャットの中で進み具合を見て、止め、要件（`focus`）や結果への追加の指示を出せる。上流の Phase 5（継続実行）は未実装なので、定期実行はしない。
モデルは上流の `optimizer_model` と `eval_model` を1つにして、そのチャットのモデルを使う。対象はロックしていないアカウントのスキル。
評価の例は、このアカウントのほかの会話（定期実行のスレッドを除く、利用者の発言と直後の応答、新しい順に300件まで）から上流の関連度判定で作り、
10件に満たなければ上流の合成で20件まで足す。秘密の文字列を含む発言は上流の検出で除き、モデルに送らない。
上流は人のレビューを経ない反映を禁じる（PR のみ）。Dahlia では、元より holdout の点数が上がり制約を満たした案だけを、
スキルの変更履歴に承認待ち（`source='optimizer'`）として置く。承認は、スキルが提案時のままの場合だけ反映し、その後は通常の取り消しができる。
実行は `agent_system_runs`（`task='optimizer'`）に残す。
