# 某アプリのミーティング開始・録音終了検出仕様

- 調査日: 2026-08-08
- 追加調査日: 2026-08-09
- 対象: 某 macOS デスクトップアプリの公開仕様と配布アプリ内の実装
- 匿名化方針: 製品名、バージョン、固有の機能名は記載しない

## 結論

某アプリは、macOS の CoreAudio が公開する「入力ストリームを実行中のプロセス」を約1秒間隔で取得し、
前回状態との差分をミーティング開始通知と録音自動停止の両方へ利用している。開始と停止は別々の
ウィンドウ判定ではなく、同じ正規化済みプロセス遷移を起点にする。

ブラウザも対象である。ただし、ブラウザ内のタブ、URL、会議サービスまでは識別せず、ブラウザアプリ単位の
音声コンテキストとして扱う。このため Chrome の通常タブ、PWA、複数の会議タブは同じ Chrome コンテキストになる。

公開ヘルプはユーザーによる停止操作を案内しているが、配布アプリ内の実装では、対応プロセスの消失から
録音停止処理へ到達する経路まで確認できた。以下は公開仕様だけでなく、配布アプリ内の実装を静的に追跡した結果である。

## 共通のプロセス観測

| 項目 | 確認できた内容 |
| --- | --- |
| 音声 API | CoreAudio のプロセスオブジェクト |
| 対象 | 入力ストリームを実行中のプロセス |
| 観測間隔 | 約1秒 |
| 正規化 | 生の bundle ID／実行ファイル名を対応アプリ種別へ変換 |
| 短い消失 | 最終観測から約4秒は同じプロセスを保持 |
| 状態差分 | 正規化後の追加を開始、消失を終了として上位層へ通知 |
| 非判定材料 | 音量、無音時間、カレンダー終了時刻、ウィンドウタイトル、タブ URL |

同じブラウザの helper process が複数存在しても、一つの正規化済みブラウザコンテキストへ集約される。
最後の該当 helper が消え、4秒の保持期間を過ぎた時点で、そのブラウザの終了遷移になる。

## ミーティング開始検知

新しい対応プロセスが現れ、ローカルの文字起こしが実行中でない場合、開始候補として通知経路へ渡す。
通知設定と権限を確認し、利用可能なら直近のカレンダー予定でタイトルなどを補完する。

通知アクションはユーザーが録音開始を選べるようにするもので、プロセス出現だけで即座に録音を開始する仕様ではない。
アプリ起動時の初期一覧は既存状態の確立に使われ、新規開始通知としては扱われない。

## 録音停止検知

対応プロセスの終了遷移を受けた際、実装は次の条件を確認する。

1. もう一度プロセス状態を問い合わせ、対象が実際に消えていることを確認する。
2. ローカル状態が録音・文字起こし中であることを確認する。
3. 録音開始から30秒未満なら停止しない。
4. 対象プロセスが設定された最低継続時間を満たしていることを確認する。
5. 条件を満たせば、音声プロセス検出を理由として通常の停止処理を呼ぶ。

先に録音を始め、その後に対応プロセスが現れた場合も、そのプロセスは停止監視の対象になる。
反対に、対応プロセスがすでに存在する状態で録音を始めた場合も、現在状態から監視対象を引き継げる。
対応プロセスを一度も観測しない対面・オフライン録音は、この仕組みだけでは自動停止されない。

## 対応コンテキスト

配布アプリ内では、少なくとも次の正規化を確認した。

- ネイティブ会議・コミュニケーションアプリ: Zoom、Teams、Slack、Webex
- ブラウザ: Chrome、Safari、Edge、Brave、Arc、Firefox
- Chromium 系の追加ブラウザ: Atlas、Comet

プラットフォーム別の実行ファイル名も同じ正規化テーブルへ統合されている。Dahlia では既存の開始検知対象との
整合性を取り、Discord、FaceTime、Chromium、Vivaldi、Opera も対応カタログへ含める。

## ブラウザ対応の意味と限界

ブラウザベースの Google Meet なども、ブラウザの音声入力 helper が CoreAudio に現れる環境では開始・停止検知を利用できる。
ただし検出対象は「Google Meet」ではなく「Chrome などのブラウザ」であり、次を区別できない。

- 会議タブと、音声入力を使う別のタブ
- 同じブラウザ内の複数会議
- 通常タブと PWA
- 会議、マイクテスト、Web 録音ツール

したがって、会議退出後も同じブラウザ内の別タブがマイクを使えば停止漏れになり得る。逆に、会議中の
デバイス切り替えやブラウザ側の入力再構成が4秒を超えると誤停止の可能性がある。CoreAudio が対象プロセスを
公開しない環境では、開始も停止も検出できない。

## Dahlia への適用

Dahlia は、開始通知を従来のマイク利用と対応アプリまたは会議ウィンドウを組み合わせる方式のまま維持する。
入力プロセスだけでは、実機検証済みの Zoom 環境で開始を検出できず、任意のブラウザマイク利用を開始と
誤通知するためである。録音停止には1秒ポーリング、4秒の消失猶予、ブラウザ単位の正規化を採用する。
安全条件として、録音と対象コンテキストがそれぞれ30秒以上継続し、録音中に監視対象となった全コンテキストが
消失した場合だけ、既存の正常停止・保存処理を開始する。

Dahlia の1秒ポーリングは、自動停止が有効な実録音中だけ実行する。録音開始前と停止・保存中には実行せず、
待機中の継続的な CoreAudio 問い合わせを避ける。

某アプリが Safari として扱う汎用 WebKit helper は、Safari 以外のアプリが所有する場合もある。Dahlia は
所有元を安全に確認できないプロセスを誤停止の根拠にせず、Safari を対象外とする。ブラウザ固有の helper を
識別できる Chrome、Edge、Brave、Arc、Firefox などは対象に含めるが、対応する会議ウィンドウを同時に
30秒間連続して観測したブラウザだけを停止監視へ登録する。資格確定前に入力プロセスまたは会議ウィンドウが
消えた場合と CoreAudio 問い合わせが失敗した場合は、同時観測時間をゼロから計測し直す。複数ブラウザが同時に
条件を満たした場合はすべてを追跡し、いずれかが残っている間は停止しない。

自動停止は既定オフである。CoreAudio 問い合わせ失敗時は既存状態を保持して停止せず、連続消失の計測をやり直す。対面会議や未対応アプリも
自動停止しない。これは誤停止を完全に排除する仕組みではなく、ブラウザ単位という制約を伴う補助機能である。
