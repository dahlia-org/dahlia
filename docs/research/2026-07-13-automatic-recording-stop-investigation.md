# ミーティング終了時の録音自動停止に関する調査

- 調査日: 2026-07-13
- 再調査日: 2026-08-08
- 状態: 某アプリの開始・停止共通実装を踏まえ、安全条件を追加して既定オフで再導入
- 対象: macOS 上の Dahlia によるマイク・システム音声同時録音

## 2026-08-09 追加調査と検知方式の再整理

配布アプリ内の Web クライアント実装まで追跡した結果、CoreAudio の入力中プロセス一覧から得た差分が、
対応アプリの出現時には開始通知、消失時には録音停止へ接続されていることを確認した。Chrome、Safari、Arc、
Firefox なども helper process の bundle ID からブラウザ単位へ正規化される。タブ、URL、会議サービスは識別しない。

Dahlia でも共通化を検証したが、既存の実機記録では Zoom の入力プロセス状態を取得できない環境があり、
ブラウザでは任意のマイク利用をミーティング開始と誤通知する。そのため、開始通知は従来のマイク利用と
対応アプリまたは会議ウィンドウを組み合わせる方式を維持し、プロセス遷移監視は既定オフの自動停止に限定した。

- 自動停止が有効な実録音中だけ、約1秒間隔で入力中プロセスを確認し、成功した問い合わせで4秒間連続して消失した場合に終了とする。
- Zoom、Teams、Slack、Discord、Webex、FaceTime と主要ブラウザを正規化済みコンテキストとして扱う。
- 初回スナップショットは状態確立に使い、録音中なら自動停止の監視対象にできる。
- 先に録音した場合は後から現れたコンテキストを追加し、会議中に録音した場合は現在のコンテキストを引き継ぐ。
- 録音と対象コンテキストがともに30秒以上継続し、録音中に監視した全コンテキストが消失した場合だけ停止する。
- 設定変更、手動停止、録音終了では監視状態をリセットする。
- 問い合わせ失敗では停止せず、最後に確定した状態を保持して連続消失の計測をやり直す。
- 対面・オフライン会議、未対応アプリ、CoreAudio に入力プロセスを公開しない環境では自動停止しない。

ブラウザは、ブラウザ固有の入力プロセスと対応する会議ウィンドウを30秒間連続して同時観測した場合だけ
停止監視へ登録する。資格確定前にどちらかが消えた場合や CoreAudio 問い合わせが失敗した場合は計測をやり直す。
登録後の終了判定はブラウザ単位であり、同一ブラウザの Meet タブと別のマイク利用タブは区別しない。
汎用 WebKit helper しか観測できず所有アプリを安全に特定できない Safari は、Dahlia の対象から除外する。
Chrome、Edge、Brave、Arc、Firefox など、ブラウザ固有のプロセスを識別できる場合に限り対応する。この制約と
確認した某アプリ側の開始・停止ロジックは、
[某アプリのミーティング開始・録音終了検出仕様](2026-08-08-reference-app-recording-stop-observation.md)にまとめた。

## 2026-08-08 某アプリの再調査と最初の限定実装（履歴）

某アプリの公開ヘルプは録音の停止操作を手動の `Stop` と案内している。一方、macOS 配布物の
デスクトップ層には、CoreAudio の入力中プロセスを継続監視する実装が含まれていた。
入力デバイスの利用状態をトリガーに 1 秒間隔でプロセス一覧を確認し、観測済みプロセスの消失を 4 秒保持してから
状態変化として通知する。該当監視経路では、無音の振幅やカレンダー終了時刻を判定材料にする処理は確認できなかった。

確認できた仕様と確認できなかった点は、
[某アプリのミーティング開始・録音終了検出仕様](2026-08-08-reference-app-recording-stop-observation.md)に分離して整理した。

Dahlia では当初、この方式を次の制約付きで再導入した。この設計は上記の2026-08-09実装で置き換えた。

- 設定は新しい UserDefaults キーで既定オフとし、削除済み設定の値を引き継がない。
- Zoom、Teams について、同じ会議コンテキストの入力プロセスと会議ウィンドウを同時に観測した録音だけを対象にする。
- armed 後も入力または会議ウィンドウの一方が残る間は録音を継続し、両方が 4 秒間連続で消失した場合だけ、既存の正常停止・保存シーケンスを開始する。
- ブラウザはマイクを使用するタブと会議セッションを安全に対応付けられないため、自動停止の対象外にする。
- Webex は通常画面と音声設定を通話中ウィンドウから安全に区別できないため、自動停止の対象外にする。
- CoreAudio 問い合わせ失敗時は停止せず、連続消失の計測をやり直す。
- 経過時間は wall clock の補正に影響されない単調時計で計測する。
- 対面会議、入力状態を CoreAudio に公開しないアプリ、未登録アプリでは自動停止しない。

この再導入は停止漏れを許容し、誤停止を抑える fail-safe な補助機能である。2026-08-03 の Zoom 実機検証では
入力状態が公開されなかったため、すべての環境で動作する保証はない。

## 当初の結論

今回確認した汎用 API だけでは、実環境のミーティング終了を誤検出なく判定できなかった。

`AVAudioEngineConfigurationChange` は Dahlia のマイクエンジンやデバイス構成の変化を通知するもので、ミーティングアプリの退出を表すイベントではない。CoreAudio のプロセス単位の入力・出力状態も、検証したミーティング中に対象プロセスを公開しなかった。

誤停止による録音欠落を避けるため、ユーザー向けの自動停止設定と実行時の自動停止処理を削除した。手動停止、致命的なキャプチャ障害時の停止、録音データの保存処理は維持する。

## 2026-08-03 再検証

前回調査の失敗原因を切り分けるため、CoreAudio のプロセス一覧とプロセス単位の入出力状態を継続監視する診断機能を追加した。
開始時の一回きりの問い合わせではなく、プロセス一覧、各プロセスの `IsRunningInput`、`IsRunningOutput` にリスナーを登録する。
一覧取得、値取得、リスナー登録・解除は OSStatus とともに `AudioProcessActivity` カテゴリへ記録し、「0 件」と問い合わせ失敗を区別する。
Dahlia 自身を含む全プロセスを記録するが、音声内容や文字起こし本文は記録しない。

署名済みの `./scripts/run-dev.sh` で起動し、Zoom ネイティブ版を実機検証した。プロセス一覧リスナーは発火し、
`us.zoom.caphost` と `us.zoom.xos` が新しい CoreAudio プロセスオブジェクトとして出現したため、前回の一回きりの一覧取得では
観測できなかったプロセス増減は確認できた。一方、両プロセスの `IsRunningInput` と `IsRunningOutput` は会議中も追加時から
`false` のままで、各プロセスへ OSStatus 0 で登録した状態リスナーも一度も発火しなかった。

この結果は「会議プロセスの入出力状態が会議中 `true` になり、退出後に `false` または消失へ遷移する」という Phase 1 の成功条件を
満たさない。Zoom だけで必須条件を満たさなかったため、ブラウザ版 Google Meet を含む Phase 2 の自動停止実装へは進まない。
会議ウィンドウ消失など別方式への転換も、この再検証のスコープでは行わない。

## 検証環境

- Dahlia は `./scripts/run-dev.sh` で起動した。
- このスクリプトは Debug バイナリを `Dahlia.app` に格納し、`Dahlia.entitlements` を付けてコード署名した後、バンドル内の実行ファイルを起動する。
- 親プロセスが Terminal であること自体は、CoreAudio が他プロセスの状態を公開するかどうかには影響しないと判断した。
- `swift run Dahlia` や `.build/debug/Dahlia` の直接実行は未署名なので、今回の権限切り分けには使用していない。

## 調査経緯

### 1. `AVAudioEngineConfigurationChange` の監視

当初の自動停止経路は、マイクの `AVAudioEngineConfigurationChange` を受け、エンジンが停止していた場合に録音停止を要求する設計だった。

実際のミーティング終了後も、ログにはマイクキャプチャ開始と最初のバッファ受信だけが記録され、次のログは発生しなかった。

```text
[MicrophoneCapture] Received microphone engine configuration change notification
```

このため、ミーティング終了時に自動停止経路へイベントが届いていないことが分かった。

### 2. 外部プロセスのマイク入力状態

CoreAudio の次のプロパティを使用し、Dahlia 自身の PID を除外して、録音開始時に入力ストリームを使用している外部プロセスを追跡した。

- `kAudioHardwarePropertyProcessObjectList`
- `kAudioProcessPropertyPID`
- `kAudioProcessPropertyBundleID`
- `kAudioProcessPropertyIsRunningInput`

実機ログ:

```text
[ExternalMicrophoneActivity] External microphone activity monitor was not armed because no other input process was active
```

ミーティング中にもかかわらず、外部入力プロセスは 0 件だった。Dahlia 自身のマイク利用を除外できる点は有効だったが、対象ミーティングアプリまたはブラウザが CoreAudio のプロセス入力状態として現れなかったため、この方式は利用できなかった。

### 3. 外部プロセスの音声出力状態

入力状態を使用せず、録音開始時から `kAudioProcessPropertyIsRunningOutput` のみを追跡する方式も検証した。これは音量の無音判定ではなく、プロセスが CoreAudio の出力ストリームを実行中かどうかを確認する方式である。

実機ログ:

```text
[ExternalAudioOutput] External audio output monitor was not armed because no other output process was active
```

入力と同様に、ミーティング中でも外部出力プロセスは 0 件だった。プロセス一覧そのものの取得に失敗した場合は別のエラーログを出す実装だったため、このログは API 呼び出しの失敗ではなく、条件に一致するプロセスが存在しなかったことを示す。

## 採用しなかった方式

### オーディオデバイス全体の使用状態

`kAudioDevicePropertyDeviceIsRunningSomewhere` は、Dahlia 自身のマイクキャプチャにも反応する。Dahlia が録音中である限りマイクデバイスは使用中になるため、ミーティングアプリの終了判定には使えない。

### システム音声の無音時間

ScreenCaptureKit が渡す音声バッファの振幅やバッファ停止時間を監視する案がある。ただし、次の状況をミーティング終了と区別できない。

- 会議中に参加者全員が発話していない
- 相手側がミュートしている
- 発表資料を黙って確認している
- ブラウザや OS が無音バッファを継続または停止する実装差

長い猶予時間を設けても誤停止の可能性は残り、短くすると録音欠落の危険が高くなる。この調査では実装を見送った。

### アプリの起動・終了

Zoom、Teams、Slack などはミーティング退出後もアプリ自体が起動し続ける。ブラウザ会議ではブラウザのプロセスも継続するため、プロセス終了はミーティング終了を表さない。

### ウィンドウタイトル

Google Meet や Zoom の会議ウィンドウをタイトルで検出できる場合があるが、次の制約がある。

- ブラウザ、言語、会議サービスの UI 更新でタイトルが変化する
- バックグラウンド、最小化、別 Space で取得結果が変わる可能性がある
- Screen Recording または Accessibility 権限の影響を受ける
- ネイティブアプリでは退出後も同じウィンドウが残る場合がある

単独の停止条件としては採用しなかった。

## 2026-07-13 時点の再検討候補（履歴）

この節は初回調査時の候補であり、2026-08-09 の再導入判断により一部は実装済みまたは置き換えられた。

自動停止を再導入する場合は、単一の汎用シグナルではなく、複数条件を組み合わせてサービス別に検証する。

1. ScreenCaptureKit の音声バッファについて、コールバック間隔、ピーク値、RMS、完全なゼロ値を診断ログへ記録する。
2. 一度有効なシステム音声を観測した後だけ無音監視を有効化し、十分に長い猶予時間を設ける。
3. 会議ウィンドウの消失やタイトル変化を補助条件にし、音声無音だけでは停止しない。
4. Google Meet、Zoom、Microsoft Teams など、対象サービスごとにミュート、長い沈黙、退出、アプリ継続のテストマトリクスを作る。
5. 自動停止前に通知またはカウントダウンを表示し、ユーザーが停止を取り消せる設計を検討する。

最低限、次のシナリオで誤停止と停止漏れの両方を確認する必要がある。

| シナリオ | 期待結果 |
|---|---|
| 通常の発話中 | 継続 |
| 参加者全員が長時間ミュート | 継続 |
| システム音声が一時的に途切れる | 継続 |
| 会議から退出し、アプリは起動したまま | 停止候補 |
| 会議終了後に別アプリが音声を再生 | 誤停止・停止漏れを評価 |
| ブラウザの別タブで音声を再生 | 誤停止・停止漏れを評価 |

## 残した診断機能

- デバッグ設定から独立ウィンドウで開くアプリケーションログ
- ログの検索、テキスト選択、表示中ログのコピー
- マイクキャプチャ開始、フォーマット、最初のバッファ、構成変更のログ
- 独立したマイク・音声認識テストウィンドウ

ログには音声内容、文字起こし本文、資格情報などのユーザーデータを含めない。

## 2026-07-13 時点で削除した機能（履歴）

以下は初回調査時の状態である。一般設定の自動停止トグルは、2026-08-09 の安全条件付き実装で
新しい UserDefaults キーとして再導入した。

- 一般設定の「録音を自動停止」トグル

- 非致命的なマイク停止を設定に応じて録音停止へ変換する判定
- 上記判定専用のテスト
